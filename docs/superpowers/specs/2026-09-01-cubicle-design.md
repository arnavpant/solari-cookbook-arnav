# cubicle — a computer-use benchmark for software that has no API

Design doc. Status: approved for planning. Date: 2026-09-01.

## 1. Problem

Every widely-cited computer-use benchmark — WebVoyager, Online-Mind2Web, Westworld —
tests agents on modern websites. Two things follow from that.

**The measurement is contaminated.** On a web page an agent can read the DOM. Even when
a harness nominally feeds it screenshots, the capability being measured is never purely
visual, and nothing in the result distinguishes an agent that *saw* a button from one
that *parsed* it.

**The market is not measured at all.** Pinetree Research's public thesis is that the
value of computer use lies in "legacy systems, dashboards, and graphical interfaces"
where automation "cannot rely on clean APIs or idealized integrations." No public
benchmark covers that. Their own headline number — 99% on WebVoyager — is saturated,
which means it can no longer discriminate between good and great agents.

`cubicle` is the missing benchmark: a real desktop accounting application, driven only
through pixels, keyboard and mouse, with objective database-backed grading.

## 2. Goals

- Measure whether an agent can complete real clerical work in a native GUI app.
- Make the measurement uncontaminated: the agent receives pixels and nothing else.
- Make grading objective and re-derivable: SQL over the application's own database.
- Make it trivially runnable by a third party, so a lab can score its own agent.
- Publish a leaderboard with a proven-solvable ceiling and an empty top row.

## 3. Non-goals

- A second application. GnuCash only.
- Cost or latency as scored dimensions (recorded, not scored).
- A web UI, a hosted service, or a CI integration.
- Any agent adapter beyond Gemini, DeepSeek, and the scripted oracle.
- Statistical rigour across many seeds. One run per (agent, task), reported as such.

## 4. The application under test

**GnuCash**, installed via `desktop.pkg.install("apt", ["gnucash"])`, using its
**SQLite backend**.

Two properties make it the right choice, both verified:

1. **It is a native GTK desktop app.** No DOM, no accessibility shortcut the agent can
   route around. Pure vision.
2. **The SQLite backend commits on every edit with no explicit save.** (GnuCash docs:
   the SQL backends "commit it immediately to the database"; the XML backend does not.)
   This matters enormously — with the XML backend every task would have partly been a
   test of whether the agent remembered to press Save.

Money is stored as an exact rational pair, `value_num / value_denom`, so `$42.50` is
`4250 / 100`. Grading compares integers. No float tolerance.

Verified schema:

```
transactions(guid, currency_guid, num, post_date, enter_date, description)
splits(guid, tx_guid, account_guid, memo, action, reconcile_state,
       reconcile_date, value_num, value_denom, quantity_num, quantity_denom, lot_guid)
accounts(guid, name, account_type, parent_guid, commodity_guid, ...)
```

### 4.1 The seed book

Every task starts from a book generated by `fixtures/build_seed.py`, which produces
`base.gnucash` plus per-task variants. **Each task owns its own seed** — tasks are
independent and never depend on another task having run.

`base.gnucash` chart of accounts (USD):

```
Assets:Checking
Assets:Savings
Expenses:Office Supplies
Expenses:Utilities:Electric
Expenses:Utilities:Water
Expenses:Technology
Expenses:Misc                  <- t03 renames this to "Miscellaneous"
Income:Consulting
```

Pre-seeded transactions in `base.gnucash`: twelve entries spanning Feb-Apr 2026 against
Checking, all with `reconcile_state='n'`. Six of them are dated in March — those are the
targets for `t06_reconcile_march`, and the non-March entries exist specifically so a
grader can catch an agent that reconciled everything indiscriminately.

Per-task seed deltas:

| Task | Seed differs from base by |
|---|---|
| t05 | adds a transaction described `Invoice 1041` for `25000/100` |
| t07 | adds account `Expenses:Software Subscriptions` (so t07 does not depend on t01) |
| t09 | omits one of the six transactions listed in the accompanying statement |
| t10 | two transactions described `Adjustment A` and `Adjustment B` |

Seeds are built programmatically rather than hand-crafted so they are reproducible and
diffable, and so a reviewer can see exactly what an agent started from.

## 5. Architecture

A local synchronous Python harness drives one remote Solari desktop per worker.

```
cubicle/
  README.md                  # the published artifact
  pyproject.toml
  cubicle/
    types.py                 # Observation, Action, Verdict, TaskResult, RunResult
    agent.py                 # the Agent protocol — the pluggable surface
    harness.py               # run loop, step caps, tracing, failure classification
    desktop.py               # Solari lifecycle, GnuCash control, slot management
    grading.py               # sqlite3 helpers shared by graders
    report.py                # results.json -> report.html + leaderboard chart
    tasks/
      __init__.py            # TASKS registry
      t01_create_account.py  # ... through t10; each: seed, prompt, grader, oracle
    fixtures/
      build_seed.py          # generates every seed book programmatically
      base.gnucash           # generated; per-task variants alongside it
    agents/
      gemini.py
      deepseek.py
      oracle.py              # scripted reference solution
  scripts/
    setup_snapshot.py        # install GnuCash, snapshot, print snapshot id
    run.py                   # CLI entrypoint
  results/<run-id>/
    results.json
    traces/<agent>/<task>/step-NNN.png
```

**Use `SyncDesktopClient`.** The rest of the SDK is `async`; a benchmark harness has no
concurrency needs beyond a two-slot worker pool, and sync removes a whole class of bugs.

### Run loop

```
setup (once per worker desktop):
    d = client.create(template="default", cpu=1, mem_mb=2048,
                      resolution="1280x720", record=True, lifecycle=<pause-on-idle>)
    d.pkg.install("apt", ["gnucash"])
    snap = d.snapshot("gnucash-clean")

per task:
    d.revert(snap)                        # pristine machine, same session id
    d.fs.write(BOOK_PATH, task.seed())    # task-specific starting book
    d.open("gnucash", [BOOK_PATH])
    wait_for_gnucash_ready(d)             # see below — NOT just health.ready
    for step in range(task.max_steps):
        obs = Observation(d.screenshot(format="png"), ...)
        act = agent.act(obs)
        if act.kind == "done": break
        apply(act)                        # mouse/keyboard only
    book = d.fs.read(BOOK_PATH)
    verdict = task.grade(local_copy(book))
```

## 6. The agent interface

The entire pluggable surface, deliberately tiny so a third party can implement it in
one sitting:

```python
class Agent(Protocol):
    name: str
    def reset(self) -> None: ...
    def act(self, obs: Observation) -> Action: ...

@dataclass(frozen=True)
class Observation:
    screenshot_png: bytes
    width: int
    height: int
    step: int
    max_steps: int
    task_prompt: str

@dataclass(frozen=True)
class Action:
    kind: Literal["click","double_click","type","key","scroll","drag","done"]
    x: int | None = None
    y: int | None = None
    text: str | None = None            # type: literal text; key: e.g. "ctrl+s"
    scroll_direction: Literal["up","down","left","right"] | None = None
    scroll_amount: int | None = None
    to_x: int | None = None            # drag target
    to_y: int | None = None
```

This maps 1:1 onto the verified SDK surface: mouse `move/click/double_click/down/up/
scroll/drag`, keyboard `type/press/hotkey/down/up`.

### Anti-cheat

`desktop.clipboard.get()/set()` exists and is **deliberately excluded** from the action
space. An agent that can read or write the clipboard is routing around the vision
requirement. The harness never exposes it, and the README says so explicitly.

Also excluded: `exec`, `fs`, `run_code`, `process`. The agent gets pixels, mouse and
keyboard. The harness uses the rest; the agent never sees it.

### 6.1 Readiness detection

`health().ready` reports that **X11** is up, not that GnuCash has finished launching.
Starting the loop on `health.ready` alone means the first several actions land on an
empty desktop or a half-drawn window.

`wait_for_gnucash_ready(d)` polls `d.process.list()` for the gnucash process **and**
takes a screenshot, advancing only when two consecutive screenshots are byte-identical
(the window has stopped repainting), with a hard timeout. GnuCash's first run also shows
a "Welcome to GnuCash" wizard; `setup_snapshot.py` dismisses it once and bakes the
dismissal into the snapshot, so no task ever meets it.

### 6.2 The agent system prompt

The prompt given to every model is **identical, fixed, and committed to the repo** at
`cubicle/agents/system_prompt.txt`. It states the action space and the response format
and nothing else — no GnuCash hints, no UI descriptions, no worked examples.

This matters for credibility. A benchmark whose prompt is tuned per model measures
prompt engineering, not agent capability. Committing one shared prompt makes the
comparison defensible and lets a third party see exactly what their agent would receive.

Models return a single JSON action per step, parsed into `Action`. A response that fails
to parse is retried once, then counted as a wasted step — mirroring what a real harness
would do rather than silently papering over it.

## 7. Task suite

Ten tasks in three tiers. Every task ships `seed()`, `prompt`, `grade(db) -> Verdict`,
and `oracle(desktop)`.

### Easy — single dialog, 15-step cap

1. **create_account** — Create an Expense account `Software Subscriptions` under
   `Expenses`.
   *Grade:* row in `accounts` with that name, `account_type='EXPENSE'`, correct
   `parent_guid`.
2. **simple_expense** — Record a $42.50 expense on 2026-03-14 to
   `Expenses:Office Supplies`, paid from `Assets:Checking`, described "Printer paper".
   *Grade:* one transaction with that description and `post_date`; two splits with
   `value_num/value_denom` of `+4250/100` and `-4250/100` against the right accounts.
3. **rename_account** — Rename `Misc` to `Miscellaneous`.
   *Grade:* `accounts.name`, same `guid` as the seeded row.

### Medium — multi-dialog, navigation or search required, 30-step cap

4. **split_transaction** — Record a $120 utility bill as $80 Electric + $40 Water,
   paid from Checking.
   *Grade:* one transaction, three splits, values `8000/100`, `4000/100`, `-12000/100`.
5. **correct_amount** — Find transaction "Invoice 1041" and change $250 to $520.
   *Grade:* splits for that `tx_guid` now `52000/100`; no duplicate transaction created.
6. **reconcile_march** — Mark all March transactions in Checking as reconciled.
   *Grade:* every split on a March-dated transaction in Checking has
   `reconcile_state='y'`; no non-March split flipped.
7. **reparent_account** — Move `Software Subscriptions` under `Expenses:Technology`.
   *Grade:* `accounts.parent_guid`.

### Hard — long-horizon, 60-step cap

8. **six_entries** — Enter six transactions listed in the prompt, in order.
   *Grade:* all six present with correct amounts, accounts and dates; no duplicates.
   *Rationale:* Pinetree's stated specialty is "long-horizon tasks where agents run many
   steps without failing." Repetitive data entry is the cheapest honest probe of that
   claim, and drift is where these agents actually die.
9. **reconcile_statement** — Reconcile against a six-line bank statement, one line of
   which has no matching transaction in the book; add the missing one, then reconcile
   all six.
   *Grade:* the missing transaction now exists with the right amount and date, and all
   six splits are `reconcile_state='y'`.
   *Note:* the statement is given as plain text **inside the task prompt**, exactly like
   t08. No second window, no file to open. Every task in this suite delivers its data
   through the prompt; the only thing on screen is GnuCash.
10. **month_end_close** — Create account `Expenses:Q1 Closeout`, then move the two
    transactions described `Adjustment A` and `Adjustment B` into it.
    *Grade:* the account exists with the right parent; the two named transactions each
    have exactly one split now pointing at it; no other split re-pointed.

Every grader also asserts **global book integrity**: for every transaction, the splits
sum to zero. An agent that corrupts the book fails even if it satisfied the specific
condition.

## 8. Grading

- Grading reads the book with Python's `sqlite3` and nothing else.
- **No LLM judge. No screenshot diffing. No human review.** A score is a fact that
  anyone can re-derive from the committed artifact.
- Each `Verdict` carries `passed: bool` plus a `reason` string naming the failed
  assertion, so a failure is diagnosable without watching the replay.
- Failures are classified: `pass`, `wrong_state`, `timeout` (step cap hit),
  `crash` (app died or session error), `corrupt` (integrity assertion failed).

### What `results.json` records per (agent, task)

`verdict` and `reason`; `steps_used` against `max_steps`; wall-clock split into model
time and desktop time; count of unparseable model responses; and the Solari `sessionId`
plus recording id so a replay can be linked from the report.

Steps and timing are **recorded but not scored** (§3). They are there so a reader can
tell a near-miss from a flail, and so the cost/latency dimension is a later analysis
rather than a re-run.

## 9. Scoring and the leaderboard

Score is tasks passed over tasks attempted, reported overall and per tier. Per-tier is
the important number: it locates the difficulty cliff even when overall scores cluster.

```
Scripted oracle      ####################  10/10   proves solvable
Gemini 2.5 Flash     ????                    ?/10
DeepSeek V4 Vision   ??                      ?/10
Pinetree-CUA         ....................     —    untested
```

**The model scores above are unknown, not predicted.** No number goes in the README
until it has actually been measured, and whatever comes out is what gets published —
including a 0/10, which would itself be a finding worth reporting honestly.

The oracle row exists to pre-empt the standard attack on any hard benchmark — "your
tasks are impossible." It is built anyway, as the validation harness for each task and
grader, so it costs nothing extra.

The empty row is a deliberate, standing invitation.

## 10. Agents under test

| Agent | Model | Cost | Notes |
|---|---|---|---|
| Gemini | `gemini-2.5-flash` | free tier | 10-30 RPM; harness must rate-limit. Free tier means Google may train on the prompts — the README says so |
| DeepSeek | `deepseek-v4-flash-vision-exp` | existing key | **images capped at 384 tokens** |
| Oracle | none | free | scripted; reference ceiling |

DeepSeek's 384-token image cap is not a defect in the benchmark — it is a finding. A
1280x720 screenshot downsampled to 384 tokens cannot resolve GUI controls. "The cheap
model cannot see the buttons" is a legitimate, publishable result, and it should be
stated plainly rather than buried.

## 11. Verified platform facts

Confirmed by introspecting `solari-desktop==0.2.0` and reading the docs, not assumed.

| Fact | Consequence |
|---|---|
| `d.snapshot(name) -> str`, `d.revert(snapshot_id)` | Revert restores the **same** machine, same session id |
| Docs describe a `fromSnapshot` create param; **it is absent from the Python SDK 0.2.0 `create()` signature** | Use `revert`. Do not design around forking |
| `d.fs.read/write/list/stat/remove/mkdir` | Direct file access; no signed-URL dance needed |
| `d.pkg.install(manager, packages)` | One-call GnuCash install |
| `create(record=True)` | Session recording on desktops — replay links for the README |
| VMs billed by vCPU/memory; live screen +$0.02/hr; $20 ~= 350 h on 1 vCPU / 2 GB | A full run is ~2 desktop-hours, i.e. pennies. Budget is a non-issue |
| Idle timeout defaults to 30 min, configurable to pause **or** terminate | Set pause-on-idle via `lifecycle` |
| A **paused** VM does not count against the running-VM limit | Pause, don't destroy, to free a concurrency slot |

**Not yet verified:** the exact shape of the `lifecycle` dict passed to `create()`. It
is typed `Optional[Dict[str, Any]]`, and the docs describe pause-vs-terminate-on-idle
behaviour without giving the key names. First task in the plan is a five-minute probe to
pin it down; until then, treat pause-on-idle as an assumption, not a fact.

### Gotchas that will cost hours if met cold

The cookbook has a "gotchas" section; these are five more it does not cover. They
belong in cubicle's README for the same reason.

1. **`429 ConcurrencyLimitExceeded` is never retryable.** A slot frees only when *you*
   pause or kill a session. The harness manages a strict two-slot semaphore and must
   never back off and retry into a concurrency error.
2. **A `200` from `exec` only means the HTTP call succeeded.** The command's real
   result is in `exitCode`. Every `exec` and `pkg.install` return must be checked.
3. **`GET /sessions/:id` always returns 404.** Never poll session status that way; use
   `health()`.
4. **Branch on HTTP status or `code`, never on the error prose** — the message is
   explicitly not stable.
5. **Retry policy differs by client.** The VM client retries any `5xx` or
   `retryable: true` up to 6 attempts; the browser client retries only 502/503/504 up
   to 2. Do not assume one from the other.

## 12. Concurrency and cost

Starter plan: **2 concurrent sandboxes/desktops**, 5-hour max session, $20 credit.

- Worker pool is hard-capped at 2 — one desktop per agent, each with its own snapshot
  (snapshots are per-machine).
- Smallest viable machine: `cpu=1, mem_mb=2048`.
- Estimated full run: 10 tasks x 3 agents ~= 2 desktop-hours, well under $1.
- Cost is not a constraint. Wall-clock and the 2-slot cap are.

### Wall-clock is the real budget

Gemini's free tier is the binding limit, not Solari. At a conservative 10 RPM and an
average of ~30 steps across the ten tasks, one Gemini run is ~300 model calls, i.e.
**~30 minutes of pure rate-limiting** before any desktop latency. DeepSeek is unmetered
by comparison. Budget roughly **45-60 minutes per full agent run**, and run the two
model agents in parallel across the two desktop slots. The oracle run is fast.

Practical consequence: iterate against a `--tasks t01,t02,t03` subset during development
and only do full runs when publishing.

## 13. Risks

| Risk | Mitigation |
|---|---|
| GnuCash not in apt, or a first-run wizard blocks the UI | Probe during setup; script past the wizard in `setup_snapshot.py` and bake it into the snapshot |
| `revert` doesn't restore cleanly enough between tasks | Fallback: kill GnuCash, delete book, rewrite seed. Detect via an integrity check after revert |
| Desktop `NoCapacityError` on create | Retryable per docs (5xx class); create once per worker, not per task, so exposure is minimal |
| GnuCash holds a lock on the SQLite file during read | `cp` the file inside the VM via `exec`, then `fs.read` the copy |
| Gemini free-tier rate limits stall the run | Harness rate-limits to 10 RPM and retries on 429 from Google (distinct from Solari's non-retryable 429) |
| Tasks too hard — everything scores 0 | The easy tier is deliberately near-trivial. If an agent scores 0/3 on easy, that itself is the finding |

## 14. Success criteria

1. `python scripts/run.py --agent oracle` scores 10/10. Without this nothing else is
   meaningful.
2. Gemini and DeepSeek each complete a full run and produce a `results.json`.
3. `report.py` renders a leaderboard chart and per-task table from that JSON.
4. A stranger can add an agent by implementing one method, documented in the README.
5. The README leads with the contamination argument, the chart, and the empty row.

## 15. Out of scope for v1

Second application. Cost/latency scoring. Multi-seed statistics. Hosted leaderboard.
CI. Any agent beyond the three named.
